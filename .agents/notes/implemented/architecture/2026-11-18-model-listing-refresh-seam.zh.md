# Agent Note: 以命名空间为键的重新加载提供项按需重新加载路由跟随的模型列表

Status: implemented

[English](2026-11-18-model-listing-refresh-seam.md) | 中文

## 问题

两条 DeepSeek 路由都从 Host 适配器里的内存缓存提供 `/models` 列表：官方路由仅在目录为内置目录时如此（[官方列表决策](2026-10-22-deepseek-official-model-listing.zh.md)），账号路由始终如此（[账号目录](2026-09-24-deepseek-account-remote-model-catalog.zh.md)）。首次使用后，缓存每隔 `modelsMaxAgeMs`（默认十分钟）自动刷新，包括页面空闲时，因此某次加载之后才发布的模型，要等到下一次后台刷新才会到达已打开的页面；而知道列表已变化的用户没有办法立即请求它。页面自己无法重新加载该缓存：缓存在适配器里，浏览器从不持有端点凭据，而现有的模型发现接缝只是询问一个草稿端点并返回候选，不会触达路由的缓存。模型页的另一个目录操作**恢复默认模型**会改变配置。

## 决策

`LlmRuntime.registerListingRefresh(settingsNs, refresh)` 为每个 settings 命名空间提供一个重新加载，并随所属 fiber 注册与释放；命名空间为空时以 `INVALID_LISTING_REFRESH` 失败，为同一命名空间重复提供时以 `DUPLICATE_LISTING_REFRESH` 失败。`LlmRuntime.refreshListing(settingsNs, provider, signal)` 使用该提供项，不存在时以 `NO_LISTING_REFRESH` 失败，否则等待拥有者的重新加载。两个方法都不读取也不写入 settings 与凭据。`@Remote('refreshListing')` 把该操作暴露给 Client，并把任何拒绝转换为携带 settings 命名空间与路由的 `RemoteError` `llm/model-listing-refresh-rejected`。`LlmConfigurableProvider.listingRefresh: true` 在目录条目上声明该能力，配置界面据此提供该操作。

### 命名空间是键

可配置提供商目录已经为每个设置界面提供 profile 的命名空间，而每个适配器插件拥有自己命名空间内的全部路由。按命名空间注册一次，使提供项可以在路由存在之前就存在——手工声明的 pi-ai 路由是之后才创建的——并在路由被替换后继续存在；一个命名空间服务多条路由时，在调用时传入路由。若以提供商路由为键，界面就必须枚举路由才能找到重新加载的拥有者，而且该路由一旦被替换，提供项就会消失。模型发现出于同样原因使用同一个键，因此界面可以从一个目录条目解析两项按 profile 的适配器操作。

### 各路由拥有自己的拒绝诊断

运行时无法判断某条路由为何不跟随列表：它的目录可能已被自定义，端点可能是网关，账号可能已退登，或者 key 缺失。每个提供商解析自己当前的配置，并用指明修复方式的诊断拒绝：官方路由在 `models` 与内置目录不同、或 Messages 的 origin 不是官方 API 时给出 `LISTING_NOT_FOLLOWED`，没有可用 key 时给出 `MISSING_CREDENTIAL`，账号路由没有 token 时给出 `ACCOUNT_SIGN_IN_REQUIRED`，而加载本身失败、继续使用内置目录时给出 `LISTING_REFRESH_FAILED`。单一的通用重新加载失败会把这些状态压成一条消息，无法说明应该恢复默认、修正端点、保存 key 还是登录。Client 将 Host 消息内联渲染在行下方，不添加自己的文案。

### 行与编辑器共用一次读取

只有当目录声明 `listingRefresh`、且用户层没有存储 `models` 时，模型行才提供该操作——这与编辑器用来标记**已自定义模型目录**的是同一次读取，因此行与编辑器不会互相矛盾。在官方路由上，存储用户层 `models` 会隐藏该操作，直到**恢复默认模型**取消该覆盖；账号路由没有 `models` 字段，所以只要该行显示，操作就保留；第三方路由不声明该能力。真正执行的重新加载会先丢弃缓存的列表再加载，最多等待路由的 `modelsTimeoutMs` 得到新列表，并在成功时发出 `llm/models-updated`，已打开的模型选择器随之重新加载；配置与页面快照都不变。行在本地报告结果：运行期间显示**正在刷新…**，成功时短暂显示**模型已重新加载**，拒绝则内联显示 Host 诊断，直到下一次尝试。

## 考虑过的替代方案

**在提供商适配器上加一个通用的 `reloadListing(provider)` 方法。** 这会把缓存列表的义务加到每个适配器上，包括模型只来自配置的路由，并迫使每个提供商自行发明重新加载的答案。能力标志加已注册的提供项让该操作保持可选，并把拒绝文案留在了解自身状态的路由里。

**复用模型发现接缝。** `discoverModels` 用一次性凭据描述一个草稿端点并返回供采用的候选元数据；它从不丢弃路由的缓存，页面也必须写端点而不是配置好的路由。通过它重新加载还会绕过路由自身的配置与拒绝诊断。

**从 Client 重新获取 settings 或目录。** 缓存在 Host 适配器进程中，因此新的页面快照或 `listModels` 读取返回的仍是同一份缓存列表；浏览器没有端点凭据，无法自行获取列表。重新加载必须在缓存所在处运行。

**以提供商路由为键提供该项。** 插件注册时路由可能尚不存在，而一个命名空间可以拥有多条路由。按路由注册需要为每条路由注册一次，会在路由替换时丢失提供项，并让界面必须枚举路由才能找到拥有者。

**所有拒绝共用一个失败 code。** 用同一个 `LISTING_REFRESH_FAILED` 表示自定义目录、非官方端点、缺失 key 与已退登的账号，会让用户看不到修复方式，因为每种状态需要不同操作。各路由自己的 code 让行可以显示指明该操作的诊断。

**在页面打开时或按更短的后台间隔刷新。** 每次页面出现就重新加载会为从不查看的用户消耗请求，而更短的间隔仍然无法回答刚刚发布模型的用户。现有的 `modelsMaxAgeMs` 刷新覆盖常规的过期；显式操作在用户提出请求的那一刻作答。

## 影响

- 该操作从不改变配置：不再跟随列表的路由需要**恢复默认模型**、正确的端点、已保存的 key 或一次登录，拒绝会指明是哪一个。
- 可见性跟随用户层的 `models`，而不是适配器解析出的目录。用户层存储一份与内置目录相同的列表会隐藏该操作，尽管路由仍在提供列表；而在 profile patch 中自定义的目录会让操作保持可见，直到重新加载以 `LISTING_NOT_FOLLOWED` 拒绝。编辑器对这些状态的标记与行一致，这是共用一次读取、而不是两处判断可能互相矛盾的代价。
- 两条 DeepSeek 路由都暴露该操作；不缓存跟随列表的第三方提供商不声明任何内容，也不会获得新控件。
- 该接缝不串行化重新加载。第二次重新加载会丢弃第一次调用进行中的加载，因此模型页在一次运行期间禁用所有刷新按钮；页面之外的 Remote 调用者仍可发起另一次。
- 成功的重新加载总会重新发布 `llm/models-updated`，因为被丢弃的缓存使随后的列表被视为变化，所以即使列表内容不变，已打开的选择器也会重新加载。
